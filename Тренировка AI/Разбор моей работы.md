В данном файле представлен детальный разбор архитектуры **AI-агента**, предназначенного для помощи сотрудникам службы поддержки. Основная цель системы — принимать запросы в свободной форме, вести диалог и самостоятельно собирать информацию из множества внутренних систем.

Ниже приведена расшифровка основных этапов проектирования и технического устройства системы:

### 1. Основная задача и интерфейс

Агент работает в формате единого чата с сотрудником. Его задачи включают:

- **Анализ запроса:** понимание намерений пользователя.
- **Сбор данных:** получение информации о профиле клиента, платежах, операциях, продуктах, документах и рисках из внутренних систем.
- **Помощь в действиях:** выполнение необходимых операций на основе анализа ситуации.

### 2. Слойность архитектуры (Layers)

Автор предлагает разделить систему на несколько уровней для эффективного управления данными:

- **Consumer Layer (Слой чата):** интерфейс взаимодействия с сотрудником.
- **Tools Layer (Слой инструментов):** здесь агент решает, к какой именно внутренней системе нужно обратиться.
- **Adapter / Function Tools:** механизмы, которые преобразуют намерения агента в конкретные вызовы API.
- **Cache Layer:** слой для хранения «горячих» ответов, чтобы не запрашивать базу данных повторно при каждом обращении.

### 3. Стек технологий и протоколы

Для взаимодействия между частями системы автор рассматривает следующие инструменты:

- **FastAPI:** основной фреймворк для создания API.
- **gRPC и GraphQL:** протоколы для взаимодействия между микросервисами и гибкого получения данных (GraphQL позволяет запрашивать только нужные поля).
- **Kafka:** используется для обработки событий в реальном времени (например, изменение статуса клиента).
- **Redis:** база данных в оперативной памяти для кэширования ответов и обеспечения низкой задержки.
- **Celery:** используется для выполнения **фоновых задач**. Если операция (например, сложный расчет рисков) занимает несколько минут, она уходит в Celery-воркер, чтобы не блокировать основной поток HTTP-запроса.

### 4. Логика обработки запроса (Data Flow)

1. Сотрудник пишет запрос в чат.
2. Запрос проходит через **API Gateway**.
3. Агент оценивает задачу и через **Function Tools** распределяет её по нужным сервисам (профиль, платежи, риски и т.д.).
4. Система проверяет наличие данных в **кэше**.
5. Если данных нет, происходит запрос к источнику, результат сохраняется в кэш и отправляется обратно сотруднику через брокер сообщений.

Автор подчеркивает, что такая структура позволяет системе быть гибкой: для коротких задач используются прямые ответы, а для длительных — фоновые воркеры.
