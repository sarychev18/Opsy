## Что такое RAG (Retrieval-Augmented Generation)

**RAG** — это когда LLM отвечает не только “из своей памяти”, а сначала **ищет информацию в базе знаний**, а потом строит ответ на её основе.

### Как это работает

1. Пользователь задаёт вопрос
2. Система ищет подходящие куски текста в документах
3. Эти куски подставляются в prompt
4. LLM отвечает уже с учётом найденного контекста

### Простыми словами

RAG — это не “модель всё знает”, а
**“модель сначала нашла нужную информацию, потом ответила”**.

---

## Зачем нужен RAG

Потому что LLM:

* может не знать внутренние документы компании
* может знать устаревшую информацию
* может начать додумывать там, где нужен точный ответ

RAG особенно полезен, когда нужно отвечать по:

* базе знаний
* внутренней документации
* FAQ
* инструкциям
* регламентам
* статьям
* support-материалам

---

## Основные шаги в RAG

* документы режутся на куски
* для кусков считаются embeddings
* они кладутся в vector storage
* по вопросу пользователя ищутся похожие куски
* найденный контекст добавляется в prompt
* модель отвечает на его основе

---

## Популярные хранилища для RAG

| Инструмент   | Что это по сути                         | Когда использовать                                             |
| ------------ | --------------------------------------- | -------------------------------------------------------------- |
| **Chroma**   | Простое векторное хранилище             | Прототипы, локальная разработка                                |
| **pgvector** | Postgres с поддержкой векторного поиска | Когда уже есть Postgres и не хочется отдельную БД              |
| **Pinecone** | Отдельная managed vector DB             | Когда нужен облачный готовый сервис                            |
| **Qdrant**   | Отдельная vector DB                     | Когда нужен production-вариант с хорошим поиском и фильтрацией |

---

## Что важно про pgvector

Если используется **pgvector**, то важно понимать:

* **без индекса** поиск будет точный, но медленный
* **с индексом** поиск быстрее, но обычно уже менее точный

Основные варианты:

* **exact search**
* **HNSW**
* **IVFFlat**

<a id="exact-search-pgvector"></a>

## Exact search в pgvector

**Exact search** — это точный поиск ближайших векторов **без approximate-индекса**.
В `pgvector` это поведение по умолчанию: база сравнивает запрос с векторами и возвращает действительно ближайшие результаты, то есть с **perfect recall**. ([GitHub][1])

### Плюсы

* максимально точный результат
* ничего не теряется из-за approximate search
* проще объяснить и отладить
* удобно как baseline для сравнения с HNSW / IVFFlat. ([GitHub][1])

### Минусы

* на больших объёмах работает медленнее
* плохо масштабируется, если данных очень много
* для тяжёлого retrieval в production может быть слишком дорогим по времени. ([GitHub][1])

### Когда использовать

* данных пока немного
* важна максимальная точность
* нужно сравнить качество approximate-индексов с эталоном
* делаешь прототип или baseline
* latency пока не критична

### Вывод

> **Exact search в pgvector — это точный nearest neighbor search без approximate-индекса. Он даёт perfect recall и удобен как baseline или для небольших объёмов данных, но на больших таблицах обычно уступает approximate-подходам по скорости.** ([GitHub][1])

<a id="hnsw-ivfflat"></a>

## Что такое HNSW и IVFFlat в pgvector

Это **типы индексов** для быстрого поиска ближайших векторов.

Они нужны потому, что когда векторов становится много, искать “в лоб” по всей таблице становится дорого.

С ними:

* поиск становится **быстрее**
* но может быть **не идеально точным**

---

## HNSW — что это простыми словами

**HNSW** — это индекс, который строит удобную “сетку связей” между похожими векторами, чтобы потом быстро идти по этим связям к нужным соседям.

* обычно даёт **хорошее качество поиска**
* часто считается **лучшим вариантом по speed/recall tradeoff**
* хорошо подходит для production
* но:

  * строится дольше
  * ест больше памяти

И `pgvector`, и Supabase в своей документации отмечают, что HNSW обычно даёт лучшую производительность / recall tradeoff, хотя требует больше памяти и более долгого построения индекса. ([GitHub][4])

### Когда нужен

Если у тебя много данных и нужен быстрый и качественный retrieval —
обычно первым смотрят именно на **HNSW**.

---

## IVFFlat — что это простыми словами

**IVFFlat** — это индекс, который сначала делит все векторы на группы,
а потом во время поиска смотрит **не во все группы**, а только в наиболее подходящие.

* строится быстрее
* требует меньше памяти
* но качество поиска обычно слабее, чем у HNSW
* особенно чувствителен к настройкам и качеству данных

Официальная документация `pgvector` описывает IVFFlat именно так: векторы делятся на lists, а поиск идёт по подмножеству списков, ближайших к запросу; build faster, uses less memory than HNSW, but has weaker speed/recall tradeoff. ([GitHub][4])

### Когда нужен

Если важны:

* более простой индекс
* меньше памяти
* быстрее build
* и ты готов мириться с более слабым качеством поиска

---

## Ключевая разница между HNSW и IVFFlat

| Индекс      | Что делает по сути                                  | Плюсы                                             | Минусы                                                      |
| ----------- | --------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------- |
| **HNSW**    | Ищет через сеть связей между похожими векторами     | Лучше качество поиска, хороший production-вариант | Дольше строится, больше ест памяти                          |
| **IVFFlat** | Делит векторы на группы и ищет только в части групп | Быстрее build, меньше памяти                      | Обычно слабее по качеству поиска, чувствителен к настройкам |

---

## Вывод

> **Если данных мало, можно обойтись exact search. Если данных много, обычно подключают approximate index. В pgvector основные варианты — HNSW и IVFFlat. HNSW чаще выбирают как более сильный вариант по качеству поиска, но он тяжелее по памяти и построению. IVFFlat легче и проще, но обычно уступает по качеству retrieval.**

## Что такое Chunk size и Chunk overlap

## Chunk size — что это

**Chunk size** — это размер одного куска текста, на которые мы разбиваем документ перед поиском.

### Пример

Исходный текст:

> AI хранит долгосрочную память, состояние диалога и важные факты о пользователе.
> Он использует поиск, память и оркестрацию шагов, чтобы отвечать с контекстом.
> Также система умеет сочетать семантический поиск, фильтры по метаданным и многошаговую логику.

### Если chunk size маленький

**Chunk 1**
AI хранит долгосрочную память, состояние диалога и важные факты о пользователе.

**Chunk 2**
Он использует поиск, память и оркестрацию шагов, чтобы отвечать с контекстом.

**Chunk 3**
Также система умеет сочетать семантический поиск, фильтры по метаданным и многошаговую логику.

**Плюс:** поиск точнее по узким кускам
**Минус:** можно потерять общий смысл

### Если chunk size больше

**Chunk 1**
AI хранит долгосрочную память, состояние диалога и важные факты о пользователе.
Он использует поиск, память и оркестрацию шагов, чтобы отвечать с контекстом.

**Chunk 2**
Он использует поиск, память и оркестрацию шагов, чтобы отвечать с контекстом.
Также система умеет сочетать семантический поиск, фильтры по метаданным и многошаговую логику.

**Плюс:** больше цельного смысла
**Минус:** можно тянуть в prompt лишний текст

---

## Chunk overlap — что это

**Chunk overlap** — это повторяющаяся часть между соседними кусками текста.

Он нужен, чтобы не потерять смысл на стыке двух chunks.

### Пример без overlap

**Chunk 1**
Victor хранит долгосрочную память, состояние диалога...

**Chunk 2**
Он использует поиск, память и оркестрацию шагов...

Если важная мысль оказалась на границе — она может потеряться.

### Пример с overlap

**Chunk 1**
Victor хранит долгосрочную память, состояние диалога и важные факты о пользователе.
Он использует поиск...

**Chunk 2**
...важные факты о пользователе.
Он использует поиск, память и оркестрацию шагов, чтобы отвечать с контекстом.

Здесь часть текста повторилась, и переход между кусками стал безопаснее.

---

## Что важно понимать про chunk size и overlap

* слишком **маленький chunk size** → теряется контекст
* слишком **большой chunk size** → в prompt попадает мусор
* слишком **маленький overlap** → можно потерять смысл на границе
* слишком **большой overlap** → лишние дубли и раздувание индекса

<a id="rag-mistakes"></a>

## Где чаще всего ошибаются в RAG

Проблема в RAG часто не в модели, а в том, что **плохо нашли контекст**.

Частые причины:

* плохая очистка документов
* неудачный chunking
* неправильно выбрана embedding model
* в prompt попадает лишний мусор
* нет фильтрации по metadata
* нет reranking
* используется только один поисковый запрос там, где нужно несколько
* не учитывается структура документа: заголовки, секции, таблицы

<a id="good-rag-additions"></a>

## Что ещё часто добавляют в хороший RAG (metadata filtering, query rewriting, multi-query retrieval, reranking, hybrid search)

* **metadata filtering** — искать только по нужному проекту, типу документа, пользователю
* **query rewriting** — переписать вопрос в форму, удобную для поиска
* **multi-query retrieval** — искать несколькими вариантами запроса
* **reranking** — сначала достать кандидатов, потом пересортировать их более сильной моделью
* **hybrid search** — сочетать semantic search и keyword search

### <a id="metadata-filtering"></a>Metadata filtering

Это когда мы ищем **не по всем документам подряд**, а только по нужной части базы.

Например:

* только по документам проекта **Victor**
* только по **FAQ**
* только по документам пользователя с `user_id = 123`
* только по статьям на русском
* только по свежим документам за последний месяц

**Зачем это нужно:**
чтобы поиск не тащил лишний мусор из нерелевантных документов.

> Фильтрация по метаданным — стандартная и очень полезная часть production retrieval-сценариев. Например, Qdrant прямо описывает фильтры по payload и другим полям как способ учесть бизнес-условия, которые не выражаются одним эмбеддингом. ([Qdrant][1])

---

### <a id="hybrid-search"></a>Hybrid search

Это когда поиск делается **не только по смыслу**, но и **по словам тоже**.

То есть мы совмещаем:

* **semantic search** — “похоже по смыслу”
* **keyword / sparse search** — “совпали важные слова или термины”

**Зачем это нужно:**
потому что чисто семантический поиск иногда плохо ловит:

* точные названия
* коды ошибок
* артикулы
* имена таблиц / API-методов
* редкие термины

**Пример:**
Если пользователь ищет
**“ошибка 403 при загрузке токена в AI API”**,
семантика может понять общий смысл,
но keyword search лучше поймает именно **403** и **AI API**.

Такой подход отдельно поддерживают vector DB вроде Qdrant; у них hybrid queries и server-side объединение результатов описаны как способ улучшить качество retrieval. ([Qdrant][2])

---

### <a id="reranking"></a>Reranking

Это второй этап поиска.

Сначала мы быстро достаём, например, **20–50 кандидатов**.
Потом отдельная модель или отдельный шаг решает:
**“какие из них на самом деле самые релевантные?”**

То есть:

1. первый поиск — быстрый, грубый
2. reranking — медленнее, но точнее пересортировывает найденное

**Зачем это нужно:**
потому что initial retrieval часто достаёт “что-то похожее”,
но не всегда в правильном порядке.

**Простыми словами:**
reranking — это
**“сначала грубо нашли, потом аккуратно пересмотрели”**.

Qdrant отдельно описывает reranking как способ улучшить точность поиска после первичного retrieval, в том числе в связке с hybrid search. ([Qdrant][3])

---

### <a id="query-rewriting"></a>Query rewriting

Это когда пользовательский вопрос **переписывают в более удобную форму для поиска**.

Потому что пользователь может спросить:

* слишком разговорно
* слишком расплывчато
* с лишними деталями
* в форме, неудобной для retrieval

**Пример:**
Пользователь пишет:
**“Почему у меня опять всё отвалилось после вчерашнего релиза?”**

Для поиска лучше преобразовать в что-то вроде:
**“ошибки после релиза, причины сбоя, регрессия после деплоя”**

**Зачем это нужно:**
чтобы поиск находил не “живой эмоциональный вопрос”,
а нормальный информационный запрос.

---

### <a id="multi-query-retrieval"></a>Multi-query retrieval

Это когда мы ищем **не одним запросом**, а несколькими вариантами.

Например, из вопроса
**“Как у нас хранится память пользователя?”**
можно сделать несколько поисковых запросов:

* “память пользователя”
* “long-term memory”
* “user profile storage”
* “memory schema”
* “как сохраняются факты о пользователе”

**Зачем это нужно:**
одна формулировка может не попасть в нужный документ,
а несколько разных формулировок повышают шанс найти релевантный контекст.

---

## Выводы

> **В реальном RAG одного vector search обычно мало. Часто нужны фильтрация по metadata, hybrid search, query rewriting, несколько поисковых запросов и reranking. То есть основная задача — не просто найти похожий текст, а найти именно тот контекст, который реально поможет модели ответить правильно.**

## Что такое zero-shot / few-shot

| Метод         | Что делает                                    | Пример                                        |
| ------------- | --------------------------------------------- | --------------------------------------------- |
| **zero-shot** | Даёт ответ без примеров в prompt              | “Классифицируй как позитивное/негативное”     |
| **few-shot**  | Даёт **несколько примеров** в prompt          | “Пример: 'Я счастлив' → позитив. Пример: ...” |
| **CoT**       | Строит цепочку размышлений (Chain of Thought) | “Сначала рассмотри шаги, потом ответь”        |

<a id="cot"></a>

## Chain-of-Thought Prompting (CoT)
Позволяет разложить задачу на шаги, чтобы LLM подумал как человек:

1. Определи тип сообщения.
2. Найди ключевые слова.
3. Сравни со списком.
4. Верни JSON.

→ Это повышает точность и предсказуемость. Часто CoT + temperature = 🔥

<a id="prompt-chaining"></a>

## Prompt chaining

**Prompt chaining** — это когда мы **не пытаемся решить всю задачу одним большим промптом**, а делим её на несколько последовательных шагов.
Следующий шаг получает результат предыдущего. Это помогает на задачах, где порядок и полнота важны. ([OpenAI Developers][1])

### Простыми словами

Вместо:

> “сразу сделай всё”

мы делаем так:

1. сначала разберись, что за задача
2. потом собери нужные данные
3. потом построй ответ
4. потом проверь его

То есть не один огромный прыжок, а **цепочка маленьких понятных шагов**. ([OpenAI Developers][1])

### Зачем это нужно

Prompt chaining полезен, когда:

* задача сложная и многошаговая,
* важен контроль над промежуточными этапами,
* один большой промпт начинает “мазать” и смешивать роли,
* нужно отдельно проверять промежуточные результаты. ([OpenAI Developers][1])

### Пример

Запрос пользователя:

**“Сделай summary инцидента за вчера и предложи, что проверить дальше.”**

Через chaining это можно разбить так:

1. выделить факты из логов и сообщений,
2. собрать краткое summary,
3. отдельно предложить следующие шаги,
4. отдельно проверить, не выдумано ли ничего лишнего.

### Где это особенно полезно

* RAG
* classification → retrieval → answer
* research
* document processing
* planner/evaluator workflow
* задачи, где хочется отделить **анализ**, **генерацию** и **проверку**. ([OpenAI Developers][1])

### Вывод

> **Prompt chaining — это способ повысить управляемость и качество на сложных задачах: вместо одного большого промпта задача разбивается на несколько последовательных шагов, где каждый шаг делает отдельную часть работы.**

<a id="self-check-reflection"></a>

## Self-check / reflection

**Self-check / reflection** — это когда мы просим модель **не остановиться на первом ответе**, а дополнительно **перепроверить результат по понятным критериям**.
Anthropic прямо рекомендует добавлять инструкцию вроде “Before you finish, verify your answer against [test criteria]”, особенно для coding и math, а OpenAI советует использовать planning/reflection как отдельный управляемый шаг в агентных workflow. ([Claude API Docs][2])

### Простыми словами

Мы как будто говорим модели:

> “Сначала реши задачу.
> А потом посмотри ещё раз: точно ли всё ок?”

### Что именно можно проверять

* не пропущены ли важные шаги
* соответствует ли ответ формату
* не противоречит ли ответ исходным данным
* не выдумала ли модель факты
* выбран ли правильный tool
* все ли требования пользователя учтены. ([OpenAI Developers][1])

### Пример

Можно попросить так:

> “Сначала дай ответ. Потом отдельно проверь:
>
> 1. все ли требования пользователя учтены,
> 2. нет ли противоречий,
> 3. не добавлены ли неподтверждённые факты.”

Или ещё проще:

> “Перед финальным ответом кратко проверь себя по критериям: точность, полнота, формат.”

### Зачем это нужно

Это особенно полезно, когда:

* задача важная и нельзя спешить,
* есть строгие критерии качества,
* модель склонна пропускать мелкие требования,
* нужен более стабильный результат без явного усложнения архитектуры. ([Claude API Docs][2])

### Важный нюанс

Self-check не делает ответ “гарантированно правильным”.
Это просто ещё один слой качества. На практике его лучше сочетать с:

* structured output,
* validation,
* tool use,
* evals,
* observability. ([OpenAI Developers][1])

### Вывод

**Self-check или reflection — это дополнительный шаг, где модель проверяет собственный результат по заранее заданным критериям. Это помогает ловить ошибки, пропуски и нарушения формата, особенно в многошаговых и чувствительных задачах.**

---

### Как это связано с CoT

Вот хорошая современная связка:

* **CoT** — попросить модель думать по шагам
* **Prompt chaining** — вынести эти шаги в отдельные этапы системы
* **Self-check / reflection** — добавить шаг проверки после основного решения

То есть:

* CoT — больше про способ рассуждения,
* chaining — про структуру выполнения,
* reflection — про контроль качества после решения. ([OpenAI Developers][1])

<a id="tool-calling"></a>

## Tool calling / function calling

**Tool calling / function calling** — это когда модель **не просто пишет текст**, а умеет выбрать нужный инструмент и передать в него аргументы.

### Простыми словами

Модель как будто говорит не
**“вот мой ответ пользователю”**,
а
**“для этой задачи мне нужно вызвать вот такую функцию с такими параметрами”**.

Потом уже твой код:

* получает этот вызов,
* реально запускает нужный tool,
* возвращает результат обратно модели,
* и модель на основе этого формирует финальный ответ. ([OpenAI Help Center][1])

### Где это используется

* сходить в базу данных
* вызвать API
* найти погоду
* создать задачу
* отправить письмо
* сходить в поиск
* запустить retrieval / RAG
* передать работу другому агенту или tool

### Зачем это нужно

Потому что сама LLM:

* не умеет по-настоящему ходить во внешний мир без tools
* не должна придумывать данные, если их можно получить из системы
* лучше работает, когда отдельно отвечает за **выбор действия**, а не за ручное “симулирование” этого действия

### Что важно понимать

**Tool calling не запускает функцию сам по себе.**
Модель только **генерирует намерение и аргументы**, а уже приложение решает:

* можно ли этот tool вызывать
* валидны ли аргументы
* надо ли запускать вызов
* что делать с ошибками. ([OpenAI Help Center][1])

### Пример

Пользователь спрашивает:
**“Какая сейчас погода в Ереване?”**

Модель может не отвечать текстом сразу, а вернуть что-то по смыслу вроде:

* tool: `get_weather`
* arguments: `{ "city": "Ереван" }`

Дальше система сама вызывает `get_weather`, получает результат и уже отдаёт человеку нормальный ответ.

### Вывод

> **Tool calling нужен, когда модель должна не только генерировать текст, но и инициировать действие: сходить во внешний API, запустить поиск, вызвать retrieval, получить данные из системы или выполнить следующий шаг workflow.**

<a id="structured-output"></a>

## Structured output / JSON mode / schema validation

### Structured output

**Structured output** — это когда мы просим модель вернуть ответ **не в свободной форме**, а в заранее заданной структуре.

Например, не просто текст, а объект вида:

```json
{
  "summary": "...",
  "priority": "high",
  "tags": ["rag", "retrieval"]
}
```

### Зачем это нужно

Чтобы ответ модели было легко:

* парсить кодом
* валидировать
* передавать дальше в pipeline
* использовать в UI
* использовать в router / planner / classifier / evaluator логике

LangChain тоже выделяет structured output как отдельную важную capability моделей, а не просто “красивый формат ответа”. ([LangChain Docs][2])

---

### JSON mode

**JSON mode** — это режим, в котором модель должна вернуть **валидный JSON**.

Но тут важный нюанс:

> **JSON mode не гарантирует, что JSON будет соответствовать нужной схеме.**
> Он гарантирует только, что ответ будет JSON, который можно распарсить. ([OpenAI Help Center][1])

То есть модель может вернуть корректный JSON, но:

* с лишними полями
* без нужных полей
* с неправильными типами
* в не той структуре, которую ты ждал. ([OpenAI Help Center][1])

---

### Schema validation

**Schema validation** — это проверка, что ответ модели реально соответствует ожидаемой структуре.

Например:

* есть все обязательные поля
* строки действительно строки
* числа действительно числа
* enum не сломан
* вложенные объекты имеют правильную форму

### Простыми словами

Это ответ на вопрос:
**“Модель вернула просто какой-то JSON или именно тот JSON, который мне нужен?”**

---

## Что сейчас считается более современным подходом

Сейчас обычно различают так:

### 1. Просто JSON mode

Подходит, если тебе достаточно “лишь бы был JSON”.

### 2. Structured Outputs / JSON Schema

Подходит, если нужно, чтобы модель следовала **конкретной схеме**.

В OpenAI это отдельно подчёркивается:
`json_object` — это старый JSON mode,
а `json_schema` / Structured Outputs — более предпочтительный вариант для моделей, которые его поддерживают. При `strict: true` модель должна следовать переданной JSON Schema. ([OpenAI Help Center][1])

### 3. Дополнительная валидация на стороне приложения

Даже если модель умеет structured output, на практике всё равно полезно иметь:

* валидацию в коде
* retries / re-ask
* fallback
* обработку ошибок

OpenAI прямо пишет, что если schema matching не гарантирован нативно, нужно использовать validation library и при необходимости retries. ([OpenAI Help Center][1])

---

## Простыми словами разница такая

* **Tool calling** — модель говорит:
  **“мне нужно что-то вызвать”**
* **Structured output** — модель говорит:
  **“я верну ответ в нужной структуре”**
* **JSON mode** — модель говорит:
  **“я верну JSON, но не обещаю, что он идеально подходит под твою схему”**
* **Schema validation** — уже твоя система проверяет:
  **“ответ действительно соответствует правилам или нет?”**

---

## Где structured output особенно нужен

* классификация запросов
* роутинг по агентам / tools
* planner / evaluator
* извлечение сущностей
* генерация данных для UI
* ответы для API
* сохранение результатов в БД
* любые места, где дальше ответ должен читать не человек, а код

LangChain прямо использует structured output, например, в routing-сценариях, где модель должна вернуть структуру для выбора нужных источников или агентов. ([LangChain Docs][3])

---

## Выводы

> **Если результат модели потом использует код, лучше не полагаться на свободный текст. Обычно либо просят structured output по схеме, либо включают JSON mode, а затем всё равно валидируют ответ на своей стороне. JSON mode гарантирует только валидный JSON, а не полное соответствие нужной схеме. Для действий во внешнем мире используют tool calling: модель выбирает функцию и аргументы, а реальный вызов уже выполняет приложение.** ([OpenAI Help Center][1])

## LangChain / LangGraph vs вызов напрямую

**Вызов напрямую**
“У меня простая задача. Я не хочу тащить лишний фреймворк. Мне проще самому вызвать модель, передать инструменты, получить ответ и самому контролировать весь поток.”

**LangChain**
“Я не хочу каждый раз вручную собирать типовые вещи. Мне удобнее взять готовые блоки и быстрее собрать рабочий сервис.”

**LangGraph**
“У меня уже не просто один вызов модели, а целый процесс. Например: сначала классифицировать запрос, потом сходить в поиск, потом решить — отвечать самому или передать человеку, потом сохранить состояние. Тут уже нужен не просто helper, а способ управлять всей логикой процесса.” ([LangChain Docs][1])

> **LangChain — про быстро собрать.
> LangGraph — про управлять сложным поведением.** 

| Подход             | Что это на самом деле                                                                                                                  | Когда использовать                                                                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **Вызов напрямую** | Ты сам напрямую говоришь модели: вот сообщение, вот инструменты, вот ответ. Без лишней прослойки                                       | Когда задача простая и ты хочешь полный контроль                                                       |
| **LangChain**      | Готовые строительные блоки, чтобы не собирать всё с нуля: подключить модель, tools, поиск по базе, structured output, агента           | Когда нужно быстро собрать рабочий LLM-сервис и не писать всю обвязку руками                           |
| **LangGraph**      | Способ собрать не просто “один запрос к модели”, а целый процесс: с шагами, развилками, циклами, памятью, паузами и возвратом к работе | Когда AI должен делать сложную многошаговую работу, где важно понимать, что происходит на каждом этапе |

## DAG

**DAG** (Directed Acyclic Graph) — это способ описать процесс как набор шагов и зависимостей между ними, без циклов.

### Простыми словами

Это схема выполнения:
что за чем идёт, что от чего зависит, и какие шаги можно запускать параллельно.

### Где используется

* data pipelines
* Airflow
* ETL / preprocessing / ML training / evaluation / deploy ([Apache Airflow][1])

### Важно

> DAG хорошо подходит для процессов с понятной последовательностью шагов.
Но в современных LLM/agent workflow этого часто уже недостаточно, потому что там бывают циклы, retries, human-in-the-loop и состояние между шагами. Поэтому там чаще используют graph-based или stateful workflow, а не только DAG. LangGraph как раз поддерживает циклические графы. ([LangChain Blog][2])

<a id="apache-airflow"></a>

## Apache Airflow

**Apache Airflow** — это оркестратор задач и пайплайнов.
Он позволяет описывать процесс как набор шагов, задавать зависимости между ними, запускать их по расписанию или по событию и следить за выполнением через UI. ([Apache Airflow][1])

### Где используется

* ETL и data pipelines
* подготовка данных
* пересчёт эмбеддингов
* индексация документов для RAG
* batch inference
* регулярные evaluation / reporting jobs
* периодические или event-driven workflow. Airflow 3.x поддерживает и event-driven scheduling, не только cron. ([Apache Airflow][3])

### Где Airflow подходит для LLM

Airflow хорош, когда процесс:

* состоит из понятных шагов
* запускается по расписанию или событию
* не требует живого “агентного цикла” с постоянным принятием решений

**Примеры:**

* раз в ночь забрать новые документы
* очистить их
* порезать на chunks
* посчитать embeddings
* обновить индекс
* прогнать evaluation на наборе вопросов

### Где Airflow уже не лучший выбор

Для интерактивных LLM/agent-сценариев Airflow часто менее удобен, потому что такие сценарии могут требовать:

* циклов
* состояния между шагами
* пауз и возобновления
* human-in-the-loop
* надёжного продолжения после падения именно с того же места

Для этого чаще смотрят в сторону **LangGraph** или **Temporal**, а не Airflow. LangGraph прямо подаётся как runtime для stateful agents с durable execution и human-in-the-loop, а Temporal — как durable workflow platform для long-running AI processes. ([LangChain Docs][2])

### Выводы

> **Airflow — это оркестратор workflow. Для LLM он отлично подходит для batch- и data-oriented процессов: ingestion, reindexing, embeddings, evaluation, scheduled pipelines. Но для интерактивных агентных сценариев с состоянием, циклами и human-in-the-loop чаще выбирают более подходящие инструменты, например LangGraph или Temporal.**

## Современные subagents / multi-agent systems

**Subagents** — это специализированные агенты, которым дают отдельные роли в рамках одной большой задачи.

### Простыми словами

Это подход, при котором не один агент делает всё подряд,
а задача разбивается между несколькими “исполнителями”:

* один ищет информацию
* другой пишет код
* третий проверяет результат
* четвёртый собирает финальный ответ

### Частый паттерн

**Orchestrator / Supervisor + Subagents**

Оркестратор:

* принимает общую задачу
* разбивает её на подзадачи
* решает, кому что передать
* собирает результаты
* проверяет, всё ли выполнено
* отдаёт финальный результат

Subagents:

* получают узкую задачу
* работают в своей специализации
* возвращают результат оркестратору

### Где это полезно

* сложные многошаговые задачи
* research по нескольким источникам
* coding + testing + review
* большие workflow, которые удобно делить на роли
* случаи, где одному агенту уже слишком тяжело держать всё в одном контексте


> Это **не единственно правильная архитектура**.
Во многих случаях один агент с хорошими tools и нормальной orchestration проще и надёжнее. Multi-agent имеет смысл, когда специализация и разделение задач реально дают выигрыш. ([LangChain Docs][6])

### Не только “оркестратор сверху”

Сейчас часто выделяют несколько паттернов:

### 1. Supervisor / orchestrator

Один координирует остальных

### 2. Handoffs

Один агент передаёт задачу другому, и управление уходит дальше по цепочке. OpenAI описывает handoffs как one-way transfer между агентами. ([OpenAI][2])

### 3. Agent as tool

Специализированный агент вызывается как “инструмент” другим агентом

### 4. Network / graph

Агенты могут обращаться друг к другу не только через одного центрального координатора

Для шпаргалки можно даже оставить только первые два — этого уже хватит.

---

### Выводы

> **Современные subagents — это способ разделить сложную задачу между специализированными агентами. Самый частый паттерн — orchestrator, который декомпозирует задачу, делегирует подзадачи subagents, собирает их результаты и формирует финальный ответ. Но multi-agent не всегда нужен: часто один агент с tools проще, дешевле и легче в отладке.**

<a id="single-vs-multi-agent"></a>

## Single-agent vs multi-agent

### Single-agent

**Single-agent** — это когда всю задачу решает **один агент**:
он сам думает, сам выбирает tools, сам делает шаги и сам отдаёт результат.

### Когда это подходит

* задача не слишком большая
* логика понятная
* инструментов немного
* не нужна сильная специализация по ролям
* важны простота, скорость и удобная отладка

### Плюсы

* проще реализовать
* проще дебажить
* дешевле
* меньше лишней orchestration
* проще писать evals

OpenAI прямо рекомендует не усложнять архитектуру раньше времени: один агент часто может покрыть много задач, если постепенно добавлять ему tools. Это упрощает поддержку и evaluation. ([OpenAI][1])

---

### Multi-agent

**Multi-agent** — это когда большая задача делится между несколькими агентами с разными ролями.

Например:

* один ищет информацию
* второй пишет код
* третий проверяет
* четвёртый собирает финальный ответ

### Когда это подходит

* задача сложная и многошаговая
* удобно делить её на роли
* нужен параллелизм
* одному агенту уже тяжело держать весь контекст
* есть отдельные типы задач: поиск, планирование, проверка, synthesis

Anthropic описывает такой паттерн как orchestrator + specialized subagents: главный агент декомпозирует задачу, подагенты делают узкие подзадачи, потом результаты собираются обратно. ([Anthropic][2])

---

### Выводы

> **Multi-agent — это не “более современно по умолчанию”.**
> Очень часто лучше начать с single-agent и переходить к multi-agent только тогда, когда реально появляются проблемы:
> 
> * слишком длинный контекст
> * смешение ролей
> * сложная orchestration
> * неудобный дебаг
> * желание распараллелить независимые шаги

LangChain тоже отдельно подчёркивает, что multi-agent нужен не всегда; есть паттерны subagents и handoffs, но single-agent во многих случаях проще. ([LangChain Docs][3])

---

### Короткая разница

| Подход           | Что это                            | Когда брать                                       |
| ---------------- | ---------------------------------- | ------------------------------------------------- |
| **Single-agent** | Один агент делает всю задачу       | Когда хочется проще, дешевле и надёжнее           |
| **Multi-agent**  | Несколько агентов с разными ролями | Когда задача большая, сложная и её выгодно делить |

<a id="router-planner-evaluator"></a>

## Router / planner / evaluator patterns

Это **типовые роли в agent-системах**.

---

### Router

**Router** — это компонент, который решает, **куда отправить задачу дальше**.

### Что он делает

Он смотрит на входящий запрос и выбирает:

* какой tool вызвать
* какого агента подключить
* к какой базе знаний обратиться
* по какому сценарию пойти дальше

### Пример

Пользователь пишет:

* “покажи погоду” → идём в weather tool
* “найди в документации” → идём в RAG
* “создай задачу” → идём в task API

В LangChain structured routing используется как отдельный паттерн: модель возвращает структуру, по которой система выбирает нужный источник, tool или workflow. ([LangChain Docs][3])

---

### Planner

**Planner** — это компонент, который решает, **какие шаги нужны для выполнения задачи**.

### Что он делает

Он не обязательно сам всё выполняет.
Его задача — разложить большую цель на шаги.

### Пример

Запрос:
**“Собери краткий отчёт по инциденту за вчера”**

Planner может разложить это так:

1. найти логи
2. собрать ошибки
3. проверить статус сервисов
4. собрать summary
5. отдать результат пользователю

Это особенно полезно, когда задача:

* большая
* состоит из нескольких стадий
* требует явной декомпозиции
* плохо решается одним прямым вызовом

В современных agent workflow planning часто входит в оркестрацию долгих задач; OpenAI и LangGraph описывают agents как системы, где модель определяет процесс и tool usage по ходу работы. ([OpenAI Developers][4])

---

### Evaluator

**Evaluator** — это компонент, который проверяет, **хорошо ли выполнена задача**.

### Что он делает

Он может:

* оценить качество ответа
* проверить, хватает ли данных
* посмотреть, не нарушен ли формат
* решить, надо ли перегенерировать
* сравнить несколько кандидатов
* проверить результат tool call или whole trajectory

### Пример

Агент сгенерировал ответ по документам.
Evaluator проверяет:

* есть ли опора на найденный контекст
* не выдумал ли агент лишнего
* соответствует ли ответ формату
* достаточно ли уверенности, чтобы отдать его пользователю

### Простыми словами

Evaluator отвечает на вопрос:
**“Это уже хороший результат или нет?”**

OpenAI отдельно подчёркивает важность evals для AI-систем, а LangSmith разбирает оценки не только финального ответа, но и траектории агента и отдельных шагов. ([OpenAI Developers][5])

---

## Как они работают вместе

Очень частая схема такая:

1. **Router** понимает, куда отправить запрос
2. **Planner** строит план шагов
3. Агент или subagents выполняют шаги
4. **Evaluator** проверяет, хороший ли результат получился
5. Если нет — система делает retry, correction или идёт по другому пути

### Простыми словами

* **Router** — кому отдать
* **Planner** — что делать по шагам
* **Evaluator** — нормально ли получилось

---

## Когда это реально нужно

Эти роли особенно полезны, когда:

* система делает больше, чем один tool call
* есть несколько путей выполнения задачи
* нужна проверка качества перед финальной отдачей
* есть multi-agent orchestration
* есть expensive steps, и важно не делать их зря

---

## Важный нюанс

Не обязательно делать три отдельных агента или сервиса.
Иногда это просто **три логические роли** внутри одной системы:

* один prompt/classifier как router
* один planning step
* один evaluation step

---

## Выводы

> **Router, planner и evaluator — это типовые паттерны agent-систем. Router решает, куда направить задачу. Planner раскладывает её на шаги. Evaluator проверяет качество результата и решает, достаточно ли он хорош. Это не обязательно отдельные агенты: иногда это просто отдельные этапы внутри одного workflow.**

## Memory: short-term / long-term / semantic / episodic

### Что такое memory в agent-системах

**Memory** — это всё, что помогает системе **не начинать каждый раз с нуля**, а помнить контекст, прошлые действия, факты о пользователе или знания, важные для следующих шагов.

### Простыми словами

Memory отвечает на вопрос:
**“Что системе нужно помнить, чтобы работать лучше не только в этом сообщении, но и дальше?”**

OpenAI в примере про state management with long-term memory notes описывает memory именно как управление тем, **что хранится, что извлекается и что подмешивается в рабочий контекст модели**. ([OpenAI Developers][1])

---

### Short-term memory

**Short-term memory** — это краткосрочная память внутри текущей сессии или текущего запуска.

Сюда обычно относится:

* текущий диалог
* последние tool calls
* промежуточные результаты
* текущее состояние workflow
* plan на эту задачу

### Пример

Пользователь пишет:

* “сначала найди ошибку”
* потом: “теперь проверь логи”
* потом: “сделай summary”

Чтобы это работало нормально, система должна помнить,
что уже было найдено на предыдущих шагах.

---

### Long-term memory

**Long-term memory** — это данные, которые сохраняются **между сессиями** и могут использоваться позже.

Сюда обычно относятся:

* предпочтения пользователя
* долгоживущие факты
* заметки о прошлых взаимодействиях
* важные решения
* накопленный профиль или персональный контекст

OpenAI в свежем cookbook по personalization показывает long-term memory notes как персистентное состояние, которое сохраняется между запусками и потом подмешивается в контекст. ([OpenAI Developers][1])

---

### Semantic memory

**Semantic memory** — это память о **фактах, знаниях, правилах и устойчивой информации**.

### Примеры

* пользователь предпочитает русский язык
* проект написан на Python и Kotlin
* у сервиса есть таблица `users`
* в компании используется pgvector
* пользователь не любит длинные ответы

### Простыми словами

Это память типа:
**“что я знаю как факт”**

---

### Episodic memory

**Episodic memory** — это память о **конкретных событиях и прошлых эпизодах**.

### Примеры

* в прошлый раз мы обсуждали RAG
* вчера пользователь просил собрать summary по собеседованию
* на прошлой неделе агент уже пытался вызвать этот API и получил 403
* в предыдущем запуске workflow этот шаг уже падал

---

## В чём разница

Очень коротко:

* **short-term** — что происходит сейчас
* **long-term** — что сохраняется надолго
* **semantic** — факты и знания
* **episodic** — конкретные события и прошлые эпизоды

---

## Что важно на практике

Memory — это не просто “склад всего подряд”.
Обычно нужно решать:

* что сохранять
* что не сохранять
* как это извлекать
* когда подмешивать в prompt
* как не тащить в контекст лишний мусор

То есть хорошая memory system — это не только storage,
но и **retrieval + selection + injection into context**.
Именно такой акцент делает OpenAI в примере по context engineering: важно не просто хранить заметки, а управлять тем, **что попадает в working memory модели в нужный момент**. ([OpenAI Developers][1])

---

## Выводы

> **В agent-системах memory обычно делят на short-term и long-term. Short-term — это текущее состояние задачи, текущий диалог и промежуточные результаты. Long-term — это то, что сохраняется между сессиями: предпочтения, заметки, важные факты. Ещё полезно различать semantic memory — факты и знания, и episodic memory — память о конкретных прошлых эпизодах. Важна не только запись памяти, но и то, как она извлекается и подмешивается в контекст модели.**

<a id="mcp"></a>

## MCP (Model Context Protocol)

**MCP (Model Context Protocol)** — это открытый протокол, который позволяет стандартным способом подключать модели и агентные системы к внешним инструментам, данным и сервисам. ([Model Context Protocol][2])

### Простыми словами

MCP — это попытка сделать **единый понятный интерфейс** между:

* агентом / клиентом
* инструментами
* данными
* внешними системами

Чтобы не писать для каждого инструмента свою уникальную интеграцию с нуля. ([Model Context Protocol][2])

---

### Что MCP даёт по сути

По-человечески, MCP говорит:

> “Вот стандартный способ, как агент может увидеть доступные инструменты, ресурсы и действия, и как он может с ними взаимодействовать.”

То есть это не “ещё одна библиотека для агентов”,
а скорее **общий язык между агентом и внешним миром**. ([Model Context Protocol][2])

---

### Где он используется

MCP применяют там, где агенту или модели нужно:

* читать данные из внешних систем
* вызывать инструменты
* работать с файлами, базами, API
* подключать новые capabilities через единый протокол

На официальном сайте MCP отдельно подчёркиваются arbitrary data access и code execution paths, а также вопросы consent, control и security — то есть протокол рассчитан на реальную работу с внешними ресурсами и действиями. ([Model Context Protocol][2])

---

### Почему MCP стал заметен

Потому что без него интеграции часто выглядят так:

* у каждого клиента свой формат
* у каждого инструмента свой коннектор
* всё сложно переиспользовать
* много ручной glue-логики

MCP пытается это стандартизировать.
По официальному roadmap на март 2026 проект уже ушёл далеко дальше идеи “просто подключить локальные tools” и теперь развивается в сторону agent communication, enterprise readiness и масштабируемых transport-моделей. ([Model Context Protocol Blog][3])

---

### Что важно понимать

MCP **не заменяет**:

* саму модель
* orchestration
* guardrails
* evals
* бизнес-логику приложения

Он решает другую задачу:
**как стандартизированно подключать контекст, ресурсы и инструменты к агенту**. ([Model Context Protocol][2])

---

### Выводы

> **MCP — это открытый протокол для стандартного подключения моделей и агентных систем к внешним данным, инструментам и действиям. По сути это общий интерфейс между агентом и внешними ресурсами. Он не заменяет orchestration или бизнес-логику, но помогает не писать каждую интеграцию вручную в уникальном формате.**

<a id="evals"></a>

## Evals: как проверять качество LLM / agent системы

**Evals** — это способ **системно проверять**, насколько хорошо работает LLM или агентная система.

### Простыми словами

Это ответ на вопрос:

**“Мы вообще уверены, что система делает то, что от неё ожидается?”**

Не по ощущениям, не по паре удачных примеров,
а на наборе понятных проверок.
OpenAI прямо описывает evals как способ программно настраивать и запускать оценки, а Anthropic — как способ увидеть проблемы до того, как они попадут в production. ([OpenAI Developers][1])

---

### Зачем нужны evals

Потому что у LLM и агентов легко возникает иллюзия, что “вроде работает”,
а потом в реальности всплывают проблемы:

* ответ неточный
* retrieval приносит нерелевантный контекст
* агент выбирает не тот tool
* planner строит странный план
* multi-agent система идёт по лишним шагам
* после маленького изменения промпта всё незаметно сломалось

Anthropic отдельно пишет, что без evals команды часто начинают ловить проблемы уже в проде и входят в реактивный режим: починили одно — сломали другое. ([Anthropic][2])

---

### Что обычно проверяют

В зависимости от системы evals могут проверять:

* качество финального ответа
* точность retrieval в RAG
* правильность выбора tool
* корректность structured output
* качество маршрутизации
* качество плана
* количество лишних шагов
* стоимость
* latency
* устойчивость к edge cases

### Простыми словами

Мы проверяем не только
**“какой получился ответ”**,
но и
**“как система к нему пришла”**.

Для агентных систем это особенно важно, потому что две одинаковые задачи могут быть решены разными траекториями, и не каждая из них хороша. Это отдельно отмечает Anthropic для multi-agent evaluation. ([Anthropic][3])

---

### Какие бывают evals

#### 1. Offline evals

Проверки на заранее подготовленном наборе примеров.

Например:

* есть вопрос
* есть ожидаемое поведение
* есть критерии оценки
* мы прогоняем систему и смотрим результат

Это удобно для:

* регрессий
* сравнения промптов
* сравнения моделей
* проверки изменений перед релизом

OpenAI рекомендует сначала собрать dataset и потом запускать evals по нему как по повторяемой процедуре. ([OpenAI Developers][1])

---

#### 2. Online / production evals

Проверки уже на реальном трафике.

Например:

* логировать реальные запуски
* смотреть, где агент ошибается
* отмечать плохие кейсы
* сравнивать версии системы
* собирать human feedback

Anthropic отдельно подчёркивает, что post-deployment monitoring обязателен, потому что pre-deployment evals не показывают всей реальной картины использования. ([Anthropic][4])

---

#### 3. Human evals

Когда результат оценивает человек.

Это особенно полезно, если нужно проверять:

* полезность ответа
* ясность
* уместность
* стиль
* бизнес-ценность

---

#### 4. LLM-as-a-judge

Когда одна модель оценивает результат другой по заданным критериям.

Это удобно для масштаба, но требует аккуратности:

* критерии должны быть понятны
* лучше иметь контрольные human checks
* нельзя слепо доверять автоматической оценке

---

### Что считается хорошим подходом

Хороший практический подход обычно такой:

1. собрать набор реальных кейсов
2. определить, что именно считается “хорошо”
3. запускать evals после изменений
4. смотреть не только на финальный ответ, но и на траекторию
5. дополнять offline evals наблюдением в production

### Примеры критериев

* ответ корректный / некорректный
* найден релевантный контекст / нет
* выбран правильный tool / нет
* JSON валиден / нет
* задача решена за разумное число шагов / нет
* стоимость не вышла за пределы / нет

---

### Вывод

> **Evals — это системная проверка качества LLM или agent-системы на наборе понятных кейсов и критериев. Обычно смотрят не только на финальный ответ, но и на retrieval, tool selection, траекторию агента, стоимость и latency. Хорошая практика — сочетать offline evals до релиза и production monitoring после релиза.** ([OpenAI Developers][1])

## Observability / tracing

**Observability** — это способность **видеть, что именно происходило внутри системы**, а не только её финальный ответ.

* какой prompt агент получил
* какой tool выбрал
* что вернул tool
* сколько было шагов
* где произошла ошибка
* где агент начал вести себя странно

LangChain прямо пишет, что trace фиксирует последовательность шагов приложения от входа до финального результата, а в агентных системах observability должна работать независимо от фреймворка. ([LangChain Docs][5])

---

### Что такое tracing

**Tracing** — это запись полного пути выполнения.

Обычно в trace попадает:

* входной запрос
* промежуточные шаги
* вызовы моделей
* tool calls
* результаты tools
* финальный ответ
* иногда оценки, ошибки, latency, токены и стоимость

OpenAI Agents SDK отдельно отмечает, что сохраняет полный trace происходящего, а OpenAI platform связывает tracing и evaluations как часть разработки агентных систем. ([OpenAI Developers][6])

---

### Зачем это нужно

Потому что в агентных системах проблема часто не в том,
что “ответ плохой”,
а в том, что непонятно **почему** он стал плохим.

Например:

* router отправил задачу не туда
* retrieval достал мусор
* tool вернул пустой результат
* planner построил лишние шаги
* evaluator пропустил ошибку
* модель зациклилась

Без tracing ты видишь только симптом.
С tracing ты видишь путь, которым система к нему пришла.

LangChain отдельно пишет, что debugging agents — это уже не только debugging кода, но и debugging reasoning/behavior. ([LangChain][7])

---

### Что обычно смотрят через observability

* какие шаги делал агент
* какие tools вызывал
* какие данные использовал
* сколько занял каждый шаг
* где выросла стоимость
* где чаще происходят ошибки
* какие траектории приводят к плохому результату
* что меняется после нового релиза

---

### Почему observability особенно важна для агентов

Потому что агент:

* может идти разными путями
* может принимать решения по ходу
* может вызывать внешние инструменты
* может останавливаться, продолжаться, retry-ить

То есть это уже не обычный “request → response”, а целая траектория поведения.
LangChain в 2026 прямо называет agent observability отдельной задачей, отличной от обычной software observability. ([LangChain Blog][8])

---

### Связь между observability и evals

> **Observability показывает, что произошло.
> Evals помогают понять, хорошо это или плохо.**

То есть:

* **tracing** даёт данные
* **evals** дают оценку

LangChain прямо пишет, что tracing — основа для debugging, annotation и evaluation, а без наблюдаемости качественно оценивать агентов трудно. ([LangChain Blog][9])

---

### Выводы

> **Observability в LLM / agent systems — это наблюдаемость за внутренним ходом выполнения: prompts, tool calls, промежуточные шаги, latency, стоимость, ошибки и траектория агента. Tracing нужен, чтобы не просто видеть плохой ответ, а понимать, на каком именно этапе система пошла не туда. Evals и observability обычно работают вместе: tracing даёт данные, evals — критерии оценки.** ([LangChain Docs][5])
